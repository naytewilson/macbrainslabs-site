A result needs a falsifier.

Compiler success does not prove hardware placement. Placement does not prove numerical fidelity. A synthetic token count does not prove throughput. Our measurement pipeline treats each as an independent claim.

01Authoring stack

The active native graph-authoring path is SwiftMIL: Swift code emits typed MILSpec Program, Function, Block and Operation structures, serializes them as a Core ML .mlpackage with a manifest and external weights, and compiles through Apple's public coremlcompiler.

A separate ANERECore path operates on existing MIL text and weight files: parsing, printing, transactional rewrites, weight-file analysis and blob-offset audits. We distinguish new-graph authoring from surgery on an already emitted graph. Python-based conversion tools serve as external reference; they are not a required local runtime dependency.

02Placement audit

Every relevant function and per-op assignment is inspected using MLComputePlan with the expected compiled artifact identity. A device preference such as .all is not treated as proof. Operators are classified by assigned compute unit, and the result names both the computation graph and the functions examined.

On the Qwen path, FP16 four-dimensional tensor shape (1,H,1,S) is a practical lowering constraint. A standalone normalization subgraph can be sent to CPU while a normalization embedded inside a convolution/matmul-anchored block can be assigned to ANE. The surrounding graph matters as much as the operator name.

KV-state operations require their own placement audit. A failing isolated slice_update experiment did not prove state writes were inherently CPU-bound; inspecting the production state pattern falsified that inference.

One such audit is published with its tools and recorded output as evidence bundle E/001. Placement is also checked when a graph is numerically correct: N/005 describes a correct ring-buffer graft that MLComputePlan placed 0 of 115 operations on the ANE.

03Numerical parity

For a sealed artifact, compare on-device outputs against a pinned reference tensor fixture. Read MLMultiArray in logical stride order, reject NaN/Inf, normalize documented layout permutations, and compare each exposed output rather than a single final-token guess.

Thresholds belong to a specific test contract, not global correctness guarantees. A diagnostic graph with extra output taps may cause the compiler to lower the program differently; its numerical differences must be reported separately from production inference.

04Performance qualification

Report input shape and what the numerator counts. For aggregate batch throughput, divide actual generated tokens across all active lanes by measured elapsed time. Avoid assigning a batch size merely by dividing a single-token dispatch latency by B or K; the compiled program must itself contain the matching dimension.

Separate cold compilation, model loading, warmup and steady-state inference. State whether a result is single-stream, aggregate batch, speculative verification or a micrograph probe; they are not interchangeable. Track thermal state and memory pressure on the 8 GB A18 Pro test machine.

05Negative results stay visible

Early work proposed a 57.3 tok/s bandwidth ceiling inferred from a compiler-reported DRAM budget and compressed model size. A K sweep contradicted the prediction; reducing weights to LUT2 also failed to improve throughput. Later observations refined the explanation again: at shallow depth, fixed dispatch cost dominates; at 28 layers, per-layer compute becomes the larger contributor.

Such reversals are part of the result. A model should be rejected as a causal explanation when it fails a straightforward counter-experiment.

06Frozen profiles

A reproducibility claim starts with a profile: a JSON declaration of the binary, inputs, parameters and number of runs. The profile's identity is the SHA-256 of its canonical JSON as read from the git commit that holds it. A hash of a working copy, or a self-declared “frozen” flag, is not accepted.

A profile is frozen in two steps, and both must come before the first counted run. First it is committed to version control, with a commit time earlier than that run's start. Then the clean-room tool writes a freeze manifest that names the profile hash, the tool commit and the inputs. A run that starts before the freeze manifest exists is not counted. It is disclosed as a pre-freeze execution.

07Run accounting

Every execution of a profile on the measurement device is written to an append-only execution log for that device. A start entry is made durable before the run begins, and a completion entry records the exit status. The clean-room tool refuses to start if the start entry cannot be made durable. It also refuses to reuse a run directory that holds any earlier artifact. These guards were merged on 3 November 2026, and the clean-room build in use includes them.

Accounting is per profile and per device, not per output folder. Every execution is listed, passed or failed. A counted run is one made after the freeze under the same tool commit. One failed counted run blocks a reproducibility claim, and disclosing the failure does not rescue it. Executions under a different tool commit, and runs that started without completing, are disclosed and not counted.

A published record states the profile hash, the number of counted runs and the total number of executions, and it lists each execution when the total exceeds the count. Record v0.2.0 discloses eight executions of profile 2f0cc0c9: five counted and three made before the freeze. One of the eight had its run folder deleted. That execution remains in the execution log and in the record.

08Claim scope and evidence labels

Each claim carries one of four labels. PROVEN means directly observed in a receipt from the measurement device. INFERRED means it follows from proven evidence but was not itself observed. SUSPECTED means plausible but not established. UNKNOWN means the evidence is insufficient.

Core ML compute-plan placement is a compiler assignment, not a hardware trace. Neural Engine execution is therefore stated as INFERRED from placement unless a hardware execution trace exists. No published record has one.

Reruns on the measurement machine are labeled as same-chip clean-room reruns on one device. They are never presented as cross-device replication, and no published record claims cross-device replication. The claim scope names the chip, hardware model, OS build and Core ML version, and each field must match the run receipts. No novelty is claimed unless a completed prior-art search supports it.

09Review before release

A finding reaches publication as one package: a canonical JSON manifest, identified by its SHA-256, that binds the finding, the evidence bundle hash, the policy digest, the receipts and the reviews. A package is never edited after submission. Any change produces a new hash and a new review. Three checks apply, in order.

  • Two independent AI reviews. An evidence reviewer and a skeptical reviewer, each a pinned model, review the exact bundle. Each review is bound to the policy digest, the bundle hash and the finding, and records its session and usage. A split verdict is a hold. Model verdicts are advisory and cannot override the gate.
  • A deterministic gate. A versioned policy module with a fixed digest checks freeze provenance, run accounting, claim scope, receipt integrity, an exact independent recompute of the published value, and prior-art coverage. Any failed check holds the package with a named reason.
  • A final reviewer. A separate reviewer, never the submitter, returns INCLUDE or HOLD for the exact package hash. The first review walks a versioned checklist item by item and reports every blocker at once. A second round checks only the listed fixes, and there is no third round. The submitter must run the reviewer's cumulative adversarial probe suite against the exact package and attach the passing output, or the package is rejected unopened. Probes are added after every miss and are never weakened to fit a package.

A held package hash, and its evidence bundle, are blocked permanently. They are never resubmitted or republished.

10Publication and verification

Only a final INCLUDE releases a package. The publication manager then issues a new semantic version: a release in the public records repository, a new version under the series concept DOI on Zenodo, an updated citation file, and a record page and feed entry on this site. Earlier tags and their bytes are never altered.

A publication is complete only when it is verified live. The tag and every asset digest must match the records index. The deposited archive must match its checksum, and its contents must equal the tagged tree. The version DOI must resolve and be registered as findable, the record must appear on the author's ORCID profile, and the record page must be served with its DOI. The manager writes a receipt of these checks and acknowledges the hand-off. A daily drift check compares every public surface with the records index, and the Publications feed re-derives each record's verification about every six hours.

11Intake: what is automated

Packages move as files, not messages. Each package is written as a read-only drop named by its hash, with a checksum sidecar and an append-only ledger entry. The receiver re-hashes the drop before acting and records its outcome. A hold, retirement or invalid verdict blocks that hash and its bundle permanently.

Since 3 November 2026 the front half runs on a schedule. Every fifteen minutes an intake scan picks up findings staged on the measurement device and runs any requested same-chip reruns of a frozen profile. It then runs both reviews, the gate and the full probe suite on the exact pipeline commit, and drops the resulting package for the publication manager. The intake never publishes.

13Authorized and bounded research

MacBrains Labs experiments on owned Apple Silicon systems and software artifacts with a lawful basis for analysis. The research includes system performance qualification, compiler output examination, binary-format inspection, native-runtime debugging, defensive code review, and validation of software and infrastructure under the operator's control. Work is conducted through public APIs and authorized userspace inspection paths; the lab does not claim privileged firmware access or unbounded authorization to assess third-party systems.

Private measurements and internal repositories are not automatically published. We publish bounded technical summaries, identify instrumentation limits, and make supporting details available for legitimate technical correspondence when shareable.
