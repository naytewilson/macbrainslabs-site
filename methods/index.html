How I check my results

I treat four things as separate claims: the model compiled, the compiler placed it on the Neural Engine, the numbers match a reference, and real text runs at a measured speed. Passing one never stands in for another. A synthetic token count, for example, doesn’t count as throughput.

What I build with

My current native path for writing graphs is SwiftMIL. I write Swift code that emits typed MILSpec Program, Function, Block and Operation structures. That code serializes them as a Core ML .mlpackage with a manifest and external weights, then compiles them through Apple’s public coremlcompiler.

A separate ANERECore path works on MIL text and weight files that already exist: parsing, printing, transactional rewrites, weight-file analysis and blob-offset audits. I keep new-graph authoring separate from surgery on a graph that’s already been emitted. Python-based conversion tools are an external reference for me. They aren’t a required local runtime dependency.

Where the compiler assigns operations

For every relevant function, I inspect each per-op assignment with MLComputePlan, using the expected compiled artifact identity. A device preference such as .all doesn’t count as proof. I sort operators by the compute unit they’re assigned to. Each result names the computation graph and the functions I examined.

On the Qwen path, an FP16 four-dimensional tensor with the shape (1,H,1,S) is a practical constraint on lowering. A standalone normalization subgraph can be sent to the CPU. A normalization embedded inside a convolution/matmul-anchored block can be assigned to the ANE. The surrounding graph matters as much as the operator’s name.

KV-state operations need their own placement audit. A failing isolated slice_update experiment didn’t prove that state writes were inherently CPU-bound. Inspecting the production state pattern ruled that inference out.

I’ve published one such audit, with its tools and recorded output, as evidence bundle E/001. I also check placement when a graph is numerically correct. N/005 describes a correct ring-buffer graft that MLComputePlan placed 0 of 115 operations on the ANE.

Are the numbers right?

For a sealed artifact, I check numerical parity by comparing the on-device outputs against a pinned reference tensor fixture. I read MLMultiArray in logical stride order, reject NaN/Inf, normalize documented layout permutations, and compare every exposed output. I don’t stop at a single final-token guess.

Identity

Each threshold belongs to one specific test contract. It isn’t a global correctness guarantee. A diagnostic graph with extra output taps may make the compiler lower the program differently, so its numerical differences have to be reported separately from production inference.

Checking speed numbers

I report the input shape and what the numerator counts. For aggregate batch throughput, I divide the tokens actually generated, across all active lanes, by the measured elapsed time. I don’t assign a batch size just by dividing a single-token dispatch latency by B or K. The compiled program itself has to contain the matching dimension.

I keep cold compilation, model loading, warmup and steady-state inference separate. I say whether a result is single-stream, aggregate batch, speculative verification or a micrograph probe. Those aren’t interchangeable. I track thermal state and memory pressure on the 8 GB A18 Pro test machine.

Where I was wrong

Early on, I proposed a 57.3 tok/s bandwidth ceiling, inferred from a compiler-reported DRAM budget and compressed model size. A K sweep contradicted that prediction. Reducing the weights to LUT2 also failed to improve throughput. Later observations refined the explanation again. At shallow depth, fixed dispatch cost dominates. At 28 layers, per-layer compute becomes the larger contributor.

Reversals like these are part of the result. A model should be rejected as a causal explanation when it fails a straightforward counter-experiment.

How a profile gets frozen

A reproducibility claim starts with a profile. That’s a JSON declaration of the binary, inputs, parameters and number of runs. The profile’s identity is the SHA-256 of its canonical JSON, as read from the git commit that holds it. A hash of a working copy, or a self-declared “frozen” flag, isn’t accepted.

A profile gets frozen in two steps, and both have to happen before the first counted run. First, it’s committed to version control, with a commit time earlier than that run’s start. Then the clean-room tool writes a freeze manifest that names the profile hash, the tool commit and the inputs. A run that starts before the freeze manifest exists gets disclosed as a pre-freeze execution, and it isn’t counted.

Logging every run

Every execution of a profile on the measurement device goes into an append-only execution log for that device. A start entry is made durable before the run begins, and a completion entry records the exit status. The clean-room tool refuses to start if the start entry can’t be made durable. It also refuses to reuse a run directory that holds any earlier artifact. These guards were merged on 3 November 2026, and the clean-room build in use includes them.

Accounting is per profile and per device, not per output folder. Every execution is listed, whether it passed or failed. A counted run is one made after the freeze, under the same tool commit. One failed counted run blocks a reproducibility claim. Disclosing the failure doesn’t rescue it. Executions under a different tool commit, and runs that started but didn’t complete, are disclosed and not counted.

A published record gives the profile hash, the number of counted runs and the total number of executions. If the total is higher than the count, it lists each execution. Record v0.2.0 discloses eight executions of profile 2f0cc0c9: five counted and three made before the freeze. One of the eight had its run folder deleted. That execution stays in the execution log and in the record.

How I label claims

Each claim gets one of four labels. PROVEN means directly observed in a receipt from the measurement device. INFERRED means it follows from proven evidence but wasn’t itself observed. SUSPECTED means plausible but not established. UNKNOWN means the evidence isn’t enough.

Core ML compute-plan placement is a compiler assignment. It isn’t a hardware trace. So I state Neural Engine execution as INFERRED from placement, unless a hardware execution trace exists. No published record has one.

I label reruns on the measurement machine as same-chip clean-room reruns on one device. I never present them as cross-device replication. No published record claims cross-device replication. The claim scope names the chip, hardware model, OS build and Core ML version. Each field has to match the run receipts. I don’t claim novelty unless a completed prior-art search supports it.

How a finding gets reviewed

A finding reaches publication as one package. The package is a canonical JSON manifest, identified by its SHA-256, and it binds the finding, the evidence bundle hash, the policy digest, the receipts and the reviews. A package is never edited after submission. Any change produces a new hash and a new review. Three checks apply, in order.

  • Two independent AI reviews. An evidence reviewer and a skeptical reviewer review the exact bundle. Each one is a pinned model. Each review is bound to the policy digest, the bundle hash and the finding, and it records its session and usage. A split verdict means the package is held. Model verdicts are advisory, and they can’t override the gate.
  • A deterministic gate. A versioned policy module with a fixed digest checks freeze provenance, run accounting, claim scope, receipt integrity, an exact independent recompute of the published value, and prior-art coverage. Any failed check holds the package and names the reason.
  • A final reviewer. A separate reviewer, never the submitter, returns INCLUDE or HOLD for the exact package hash. The first review walks a versioned checklist item by item and reports every blocker at once. A second round checks only the listed fixes, and there’s no third round. The submitter has to run the reviewer’s cumulative adversarial probe suite against the exact package and attach the passing output. Otherwise the package is rejected unopened. Probes get added after every miss, and they’re never weakened to fit a package.

A held package hash and its evidence bundle are blocked permanently. Neither one gets resubmitted or republished.

How a record gets published

Only a final INCLUDE releases a package. Then the publication manager issues a new semantic version. That includes a release in the public records repository, a new version under the series concept DOI on Zenodo, an updated citation file, and a record page and feed entry on this site. Earlier tags and their bytes are never altered.

A publication only counts as complete once it’s verified live. The tag and every asset digest must match the records index. The deposited archive has to match its checksum, and its contents have to equal the tagged tree. The version DOI has to resolve and be registered as findable. The record has to appear on my ORCID profile, and the record page has to be served with its DOI. The publication manager writes a receipt of these checks and acknowledges the hand-off. A daily drift check compares every public surface with the records index. The Publications feed re-derives each record’s verification about every six hours.

What’s automated at intake

Packages move as files, not messages. Each package is written as a read-only drop named by its hash. It comes with a checksum sidecar and an append-only ledger entry. The receiver re-hashes the drop before acting, then records its outcome. A hold, retirement or invalid verdict blocks that hash and its bundle permanently.

Since 3 November 2026 the front half runs on a schedule. Every fifteen minutes, an intake scan picks up findings staged on the measurement device. It runs any requested same-chip reruns of a frozen profile. Then it runs both reviews, the gate and the full probe suite on the exact pipeline commit. It drops the resulting package for the publication manager. The intake never publishes.

What I work on, and its limits

I experiment on Apple Silicon systems I own, and on software artifacts I have a lawful basis to analyze. My research covers system performance qualification, compiler output examination, binary-format inspection, native-runtime debugging, defensive code review, and validation of software and infrastructure under my control. I work through public APIs and authorized userspace inspection paths. I don’t claim privileged firmware access, and I don’t claim unbounded authorization to assess third-party systems.

Private measurements and internal repositories aren’t published automatically. I publish bounded technical summaries, identify instrumentation limits, and make supporting details available for legitimate technical correspondence when they can be shared.
