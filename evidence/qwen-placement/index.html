02Model under test

The measured artifact is qwen25_monolithic_full_lut4.mlmodelc. It is a Core ML conversion of Qwen/Qwen2.5-1.5B-Instruct produced with ANEMLL's Qwen2.5 converter: monolithic export, 512-token context, LUT4 palettization, argmax output. The model's metadata records coremltools 9.0 and ANEMLL v0.3.5.

Credit

The conversion that makes this model ANE-resident is ANEMLL's work. This record measures where that model's operations are assigned and what that says about the KV-state path. It does not claim the converter.

The compiled model is not distributed here. It is derived from the Qwen weights; its stored weight file is about 893 MB.

04Rerun it

  1. Convert Qwen/Qwen2.5-1.5B-Instruct with ANEMLL's convert_monolith.sh at context 512 with LUT4 weights and argmax output, then compile the package with xcrun coremlcompiler compile.
  2. Build and run both tools against the compiled model's infer function:
swiftc -O ane_compute_plan.swift -o ane_compute_plan
swiftc -O kv_placement.swift -o kv_placement
./ane_compute_plan qwen25_monolithic_full_lut4.mlmodelc infer
./kv_placement qwen25_monolithic_full_lut4.mlmodelc infer

Compare the output with recorded_output.txt. These build commands are the standard way to compile a single Swift file. They were not rerun for this bundle.

Different converter flags can change the graph and therefore the counts. If your counts differ, the model's ANEMLL version, LUT settings and argmax setting are the first things to compare.

05Reruns, 30 October 2026

Three runs were made on 30 October 2026 with the two tools in this bundle, on Mac17,5 (Apple A18 Pro), macOS 27.2 build 26B123, with the tools built by Apple Swift 6.4.2.

The archived June artifact

A copy of qwen25_monolithic_full_lut4.mlmodelc sits in two project archives dated 12 and 23 June 2026, with the same model.mil in both. Its metadata records ANEMLL v0.3.5 and coremltools 9.0, and its weight file is 893,118,592 bytes. Run on the current OS, its infer function gave the recorded June counts exactly, including the KV-state counts.

The June record holds no model hash, so it cannot confirm that this copy is the file measured on 18 June. That is inferred from the archive dates and the identical counts.

The current shipped build

The same tools were also run on the current shipped build of the same model line, which has an infer function and a 64-token prefill function. It is a different artifact from the June one, so its counts are reported beside the June result and do not replace it.

06What it shows

MLComputePlan is the compiler's assignment, not a hardware trace. These counts show where Core ML planned each operation of this build. They do not prove zero CPU work across the whole inference stack, and they do not transfer automatically to a different Core ML build.

The KV-state counts correct an earlier claim in the same research record. An earlier note said slice_update and write_state were an irreducible CPU floor. That came from a hand-written toy graph, not from a hardware limit. In the infer function of this production graph, all four KV-state operators are assigned to the ANE.

07Gaps in the record

A reader should know what this bundle cannot supply.

  • No raw, timestamped log of the June run is in the record. Its numbers come from the findings document, the output block reproduced in the gate source, and a project archive entry dated 18 June 2026.
  • The archive gives Mac17,5 and macOS 26 beta 26A5353q in the same dated section as the result, but not on the result line itself.
  • The exact conversion command and ANEMLL commit for the June artifact were not recorded, and the June record holds no model hash. The archived copy rerun here is identified by its archive dates and matching counts, not by a recorded hash.
  • All 30 October runs record their raw output, OS build, device and model hashes. The compiled models themselves are not distributed.
