Model under test

The measured artifact is qwen25_monolithic_full_lut4.mlmodelc. It’s a Core ML conversion of Qwen/Qwen2.5-1.5B-Instruct, made with ANEMLL's Qwen2.5 converter: monolithic export, 512-token context, LUT4 palettization and argmax output. The model’s metadata records coremltools 9.0 and ANEMLL v0.3.5.

Credit

The conversion that makes this model ANE-resident is ANEMLL’s work. This record measures where that model’s operations are assigned, and what that says about the KV-state path. It doesn’t claim the converter.

The compiled model isn’t distributed here, and it’s derived from the Qwen weights. The model’s stored weight file is about 893 MB.

Tools

Both tools are short Swift programs that use only the public MLComputePlan API (macOS 14.4 or later). They’re byte-for-byte copies from the ane-re repository at commit ffd1a3c.

Rerun it

  1. Convert Qwen/Qwen2.5-1.5B-Instruct with ANEMLL’s convert_monolith.sh at context 512 with LUT4 weights and argmax output, then compile the package with xcrun coremlcompiler compile.
  2. Build and run both tools against the compiled model’s infer function:
swiftc -O ane_compute_plan.swift -o ane_compute_plan
swiftc -O kv_placement.swift -o kv_placement
./ane_compute_plan qwen25_monolithic_full_lut4.mlmodelc infer
./kv_placement qwen25_monolithic_full_lut4.mlmodelc infer

Compare the output with recorded_output.txt. These build commands are the standard way to compile a single Swift file. They weren’t rerun for this bundle.

Different converter flags can change the graph, and with it the counts. If your counts differ, check the model’s ANEMLL version, LUT settings and argmax setting first.

Reruns, 30 October 2026

I made three runs on 30 October 2026 with the two tools in this bundle, on Mac17,5 (Apple A18 Pro), macOS 27.2 build 26B123, with the tools built by Apple Swift 6.4.2.

The archived June artifact

A copy of qwen25_monolithic_full_lut4.mlmodelc sits in two project archives dated 12 and 23 June 2026. The model.mil is identical in both. Its metadata records ANEMLL v0.3.5 and coremltools 9.0, and its weight file is 893,118,592 bytes. On the current OS, its infer function gave the recorded June counts exactly, KV-state counts included.

The June record has no model hash, so it can’t confirm that this copy is the file measured on 18 June. That link is inferred from the archive dates and the identical counts.

The shipped artifact’s release notes say how it was built: ANEMLL at commit cc818aeb, convert_monolith.sh with context 512, batch 64, LUT 4 and 8, LUT4 embeddings and LM head, and argmax output, converted on 21 October 2026. On these runs I only checked the file hashes and the counts.

What it shows

MLComputePlan reports the compiler’s assignment. It isn’t a hardware trace. These counts show where Core ML planned each operation in this build. They don’t prove zero CPU work across the whole inference stack. They also don’t carry over automatically to a different Core ML build.

These KV-state counts correct an earlier claim in the same research record. An earlier note said slice_update and write_state were an irreducible CPU floor. That came from a hand-written toy graph, not from a hardware limit. In the infer function of this production graph, all four KV-state operators are assigned to the ANE. The shipped prefill function differs: one of its 57 read_state operations is assigned to the CPU.

Gaps in the record

Here’s what this bundle can’t supply.

  • The record has no raw, timestamped log of the June run. Its numbers come from the ANE-RE FINDINGS document, the output block reproduced in the gate source, and a project archive entry dated 18 June 2026.
  • The archive gives Mac17,5 and macOS 26 beta 26A5353q in the same dated section as the result, but not on the result line.
  • The exact conversion command and ANEMLL commit for the June artifact weren’t recorded, and the June record has no model hash. The archived copy rerun here is identified by its archive dates and matching counts, not by a recorded hash.
  • Each 30 October run has its raw output and model file hashes in provenance.json. That file also lists the device and OS build for each run. Only the shipped infer output carries the OS and device lines itself. The June copy and shipped prefill outputs don’t. The compiled models themselves aren’t distributed.
