MacBrains Labs / Defensive research / Derivative-record validation

Inconsistent validation of derivative research records.

A result-recording path could create an authoritative derivative without the gate applied to ordinary writes. The repair closes that inconsistency, not the broader problem of authenticating evidence.

01Finding and impact

A derivative-write path in the private research-recording tool could create caller-influenced PROVEN/RESOLVED records without the shared validation used by ordinary writes. The demonstrated defect was omission of required falsifier metadata: a record of what would contradict the claim.

A downstream consumer could treat such a record as more authoritative than the tool's checks justified. The demonstrated scope is internal evidence integrity, not an established remote authentication break, cryptographic forgery or third-party compromise.

02Corrective change

The recorded repair applies shared validation to both result branches and changes attribution to distinguish a caller's claimed evaluation from an executed measurement.

Remaining limitation

The gate validates evidence structure, not authenticated measurement provenance. A later false claim still entered the record store and was detected and corrected through source and artifact checks. This repair does not establish complete prevention of false evidence or prompt injection.

03Recorded comparisons

A later driver used the existing local MCP interface in separate copies of the vulnerable source, repair and pinned later source. It appended the same synthetic fixture and recorded a successful-result derivative. The measurement-like fixture text was synthetic input, not an actual hardware measurement.

All three server runs recorded exit status 0 and successful initialization. The direct comparison checks the successful-result metadata branch, which the existing fixture did not explicitly assert.

The current record-validation suite passed 45/45 checks on the pinned later source. On unchanged pre-repair implementation with the same current fixtures, 38 passed and 7 failed. Six failures were adversarial assertions; the seventh concerned a historical-ledger data expectation. It is not counted as a security repair.
