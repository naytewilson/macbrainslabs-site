The chain missed the gate.

Each piece of LFM2.5-1.2B met a strict parity gate on the Neural Engine. Chained together, the same pieces missed it. Parts that pass one at a time don’t add up to a passing model.

Next: the two grafts

Slices on the Neural Engine

LFM2.5-1.2B has 16 layers. The model was emitted in Swift as separate Core ML packages: layers 0-4, 0-8, 8-16 and the final norm plus tied LM head. Each package ran under .cpuOnly and under .cpuAndNeuralEngine. Each output was compared with a pinned Hugging Face PyTorch oracle for the same layer range.

The gate is strict: cosine ≥ 0.9999 and relative L2 ≤ 0.005. It applied to the Neural Engine run as well as the CPU run. Every slice passed. MLComputePlan placed every assigned compute operation on the ANE.

“Assigned ops” leaves out operations MLComputePlan gives no device, such as constants. The 0-8 and 8-16 packages also passed a weight integrity check: 70/70 and 76/76 tensors were byte-identical to the source. The final head’s top-1 token matched the oracle’s (21134).

The chained run

Feeding the ANE output of layers 0-8 into the ANE package for 8-16, with no oracle in between, gave a 16-layer hidden state with relative L2 0.005975. That misses the 0.005 gate. The same chain on CPU stayed at 0.001204.

16-layer chainCosineRel. L2Result
CPU → CPU0.9999992760.001204Pass
ANE → ANE0.9999894190.005975Fail

A follow-up breakdown split the chained error into three parts of similar size: the 0-8 package’s own error (0.003764), the 8-16 package’s own error (0.003660), and the effect of passing a slightly wrong input forward (0.003949). None of them fails alone. Together they cross the line. The receipts suggest the cause is FP16 accumulation drift in chunked matrix multiplies on the ANE. That’s still a hypothesis. I haven’t isolated it yet.

What it does and doesn’t show

Takeaway

Parity on each slice doesn’t carry over to the chain. Each package can meet the error budget, and the chain can still exceed it. A matching top-1 token can also hide logits that are measurably wrong. Gate the exact chain you plan to run, at the output you plan to use.

It shows that the whole 16-layer LFM2.5 stack can be placed on the ANE in two packages plus a head, and that the per-package numerics are close to the oracle. It doesn’t show a working ANE model. Token-level parity failed, and generation quality wasn’t measured. Later builds changed these packages, so this note covers only the 17 July receipts.

In progress: a bigger output-projection gain

Related work on a later model, LFM3-1.7B, is testing one numerical lever: the output-projection gain setting (--attn-o-gain) of a single FP16 attention layer, layer 14. On 30 October 2026, five builds were compared against a teacher at seven positions.

Gain 16 improved all seven positions. A follow-up on nineteen positions, ten of them held out, improved all nineteen (held-out worst −7.2%). The gain-8 rebuild reproduced the existing build’s hidden states exactly. That’s the control.

Status: not a result yet

One layer, nineteen positions at most, and a planned placement rather than a traced dispatch. It isn’t a full-model or release result, and it may not hold across 24 layers.
