Every slice passed. The chain did not.

Each piece of LFM2.5-1.2B met a strict parity gate on the Neural Engine. Chained together, the same pieces missed it. Passing parts are not a passing model.

01Slices on the Neural Engine

LFM2.5-1.2B has 16 layers. The model was emitted in Swift as separate Core ML packages: layers 0-4, 0-8, 8-16 and the final norm plus tied LM head. Each package ran under .cpuOnly and under .cpuAndNeuralEngine, and each output was compared with a pinned Hugging Face PyTorch oracle for the same layer range.

The gate here is strict: cosine ≥ 0.9999 and relative L2 ≤ 0.005, applied to the Neural Engine run as well as the CPU run. Every slice passed, and MLComputePlan placed every assigned compute operation on the ANE.

02The chained run

Feeding the ANE output of layers 0-8 into the ANE package for 8-16, with no oracle in between, gave a 16-layer hidden state with relative L2 0.005975. That misses the 0.005 gate. The same chain on CPU stayed at 0.001204.

16-layer chainCosineRel. L2Verdict
CPU → CPU0.9999992760.001204Pass
ANE → ANE0.9999894190.005975Fail

A follow-up decomposition split the chained error into three parts of similar size: the 0-8 package’s own error (0.003764), the 8-16 package’s own error (0.003660), and the effect of passing a slightly wrong input forward (0.003949). None of them fails alone. Together they cross the line. The receipts route the cause to FP16 accumulation drift in chunked matrix multiplies on the ANE; that cause is a hypothesis, not yet isolated.

04What this does and does not show

Experimental takeaway

Per-slice parity does not compose. An error budget that each package meets can still be exceeded by the chain, and a matching top-1 token can hide logits that are measurably wrong. Gate the exact chain you plan to run, at the output you plan to use.

It shows that the whole 16-layer LFM2.5 stack can be placed on the ANE in two packages plus a head, and that the per-package numerics are close to the oracle. It does not show a working ANE model: token-level parity failed, and no generation quality was measured. Later builds changed these packages; this note covers the 17 July receipts only.

05In progress: a larger output-projection gain

Related work on a later model, LFM3-1.7B, is testing one numerical lever: the output-projection gain setting (--attn-o-gain) of a single FP16 attention layer, layer 14. On 30 October 2026, five builds were compared against a teacher at seven positions.

Gain 16 improved all seven positions, and a follow-up on nineteen positions, ten of them held out, improved all nineteen (held-out worst −7.2%). The gain-8 rebuild reproduced the existing build’s hidden states exactly, which is the control.

Status · not a result yet

One layer, a few dozen positions, and a planned placement rather than a traced dispatch. It is not a full-model or release result, and it may not hold across 24 layers.
