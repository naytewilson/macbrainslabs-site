Placement in the production graph

The measured infer graph of the production ANEMLL Core ML conversion (qwen25_monolithic_full_lut4) assigned 2,090 operators to ANE and 79 to CPU (96.4% versus 3.6%). Those counts come from the June 2026 measurement. A later shipped build of the same model line, recorded as converted on 21 October 2026, gave 2,147 ANE and 82 CPU in its infer function. E/001 reports both builds side by side. The CPU-assigned operations sat in the language-model-head argmax/output tail. That split matters. The layer stack and KV machinery can be ANE-resident while the output selection tail is not.

The stateful pattern used padded widths, sequence geometry and graph structure that fit the compiler’s lowering rules. A failing isolated slice_update micrograph was not evidence that state writes need CPU execution in the production graph.

On the ANE, gather needs integer indices

Core ML’s ANE lowering accepted FP16 data and output gather tables with integer indices. Floating-point gather indices were not a valid substitute. FP16 can’t represent every integer precisely beyond 2,048, so forcing token IDs through that type creates both compilation and correctness hazards.

// Conceptual lowering contract
position_fp16
  └─ cast(to: uint16)
       └─ gather(fp16_rope_table, index: uint16)
            └─ fp16_rope_embedding

// NOT an ANE lowering contract
gather(data: fp16, index: fp16)

Looking up tokens in the model’s vocabulary can stay outside the ANE computation boundary, while the ANE receives FP16 embedding tensors. I treat that as data movement. I don’t label it as an ANE compute operation.

The compiler error was ambiguous

One graph failed in CreateBnnsGraphProgramFromMIL with Invalid sentinel in blob_metadata. The message was ambiguous. An unlowerable operator or an external-weight offset landing in the wrong bytes could produce a related failure. The right check was to walk every BLOBFILE offset that MIL references.

Appending new blobs without rewriting every existing offset keeps the original graph’s references intact. A “clean” MIL rewrite isn’t enough if the new weight references never got correctly indexed backing blobs.

Quality is a separate question

After the RoPE and blob-reference fixes, the hand-authored LUT4 28-layer model, run as two 14-layer halves that share KV, measured 16.8033 perplexity on WikiText-2 over the full 12,000-token validation set. It differed from an Apple Core AI comparison figure (14.79 macOS) by approximately 2.01 perplexity points. That reference is a different model and configuration. It doesn’t establish a general quality penalty for four-bit quantization.

What this covers and what it doesn’t

Claim class: on-device placement

The 2,090/79 operation counts and the four stateful-op counts came from MLComputePlan, run on the named compiled artifact. They don’t prove zero CPU work in the whole inference stack, privileged access to ANE firmware, or that the result carries over to a different Core ML build. The tools and recorded output are in evidence bundle E/001.
