I got the ceiling wrong.

A plausible throughput explanation failed. Under a controlled change to input geometry and weight size, the behavior it predicted didn’t show up.

The first explanation I liked

The compiler’s analytics.json showed an internal DRAM bandwidth planning figure of 51.2 GB/s. Dividing that number by the as-stored 893 MB external weight file gave about 57.3 tokens/sec, close to an early peak. It seemed to support a hard bandwidth ceiling.

But having the right units doesn’t make it a causal test. The calculation predicted two things. Halving the bytes read per token would increase throughput. And more real work per dispatch would still be held to that same byte rate.

What the experiments showed

Two observations broke that model. First, the smaller LUT2 weights didn’t give the matching speedup. Second, a K sweep (batch K per dispatch, on a probe model) moved useful work faster than the supposed throughput limit allowed. I retracted the “57.3 tok/s ceiling” as a K=1 coincidence, not treated as an ANE architectural law.

Later work refined the picture. Fixed per-call dispatch costs matter in shallow graphs. At 28-layer production depth, per-layer compute takes up more of each step. The lever that’s been demonstrated is multi-lane execution, not arithmetic on weight bytes alone.

These are aggregate throughputs from five interleaved rounds of steady-state measurements. B=4 is the efficiency knee on the 8 GB machine, where bigger batches start giving less back. These aren’t a single stream’s token rate, and they aren’t a measure of end-to-end app experience.

This is a throughput result only. The sweep timed single-function probe artifacts that had a real batch dimension. A later perplexity check on the B=4 probe, dated 3 July 2026, found its output logits roughly 1000 times larger than the B=1 model’s. The repo’s current records don’t resolve that. The same records say the batch geometry hadn’t been carried into a deployable multi-function model yet.

What counts as a speed result

ACCEPT only if:
  1. compiled input tensor has real [B, ...] shape
  2. elapsed time scales with actual B work
  3. reported tokens = work actually executed
  4. source artifact and device are named

REJECT:
  fixed [1,1] model + posthoc divide by K
  synthetic tokens from a benchmark argument
  projected tokens/sec treated as measured

The project rejected a K=16 throughput claim. It came from a shape-locked [1,1] compiled model and a post-hoc divisor. Its reported wall time stayed flat while the headline token rate went up, which pointed to arithmetic, not extra hardware work.

What to take forward

Bounded conclusion

On the tested Qwen decode setup, real batch geometry increases aggregate throughput. At shallow depth, dispatch overhead is a real cost. At 28 layers, the compute load changes what limits speed. No single constant pulled from a compiler report should be published as a universal throughput ceiling.
