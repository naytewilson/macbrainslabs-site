The sealed production run

The sealed LFM block-pair S2 artifact had two declared outputs and an input fixture with shape [1,2,2048]. My native runner loaded it under .cpuOnly and .cpuAndNeuralEngine, rejected non-finite values, and compared both outputs against the same pinned FP16 fixture.

MLComputePlan assigned 743/743 compute operations to ANE in the production graph. Both outputs met the established ANE tolerance: cosine similarity ≥ 0.999 and relative L2 ≤ 0.03.

lfm_h_after_liv0.9998862200.017295585Pass
lfm_h_after_gqa0.9997610050.027863104Pass

A debug build is a different artifact

Recompiling with LFM_PARITY_DEBUG=1 added 46 output taps instead of two. All 46 outputs passed the CPU-versus-fixture gate, but only 34/46 passed the ANE gate. The first ANE-gate failure reported was liv_14_mlp_output.

Diagnostic outputANE cosineANE relative L2
liv_14_mlp_output0.9979367670.064227031
gqa_15_head_merge0.0989214681.342520581

It would be wrong to treat that diagnostic result as a failing production model. Extra outputs change the compiled graph, so the diagnostic package is a different program from the production one. I keep the negative diagnostic result, but I tie it to its own model package and compiled identity.

How the native runner checks parity

The runner reads the binary FP16 fixture directly. It rebuilds the logical tensor order from MLMultiArray strides, normalizes the documented output layout permutations, and checks for NaN and Inf before it computes max absolute error, mean absolute error, cosine similarity and relative L2.

production:
    outputs = 2
    assigned_ANE_compute_ops = 743 / 743
    parity_ANE = PASS / PASS

diagnostic:
    outputs = 46
    CPU_parity = 46 / 46
    ANE_parity = 34 / 46
    verdict = ANE_ONLY_DIVERGENCE

these are DIFFERENT compiled artifacts

What the receipt pins down

The receipt pins SHA-256 identities for the source, the runner, the fixture tree, the emitted model package, the compiled graph and the report. The sealed production model.mlmodel SHA-256 is 3935a7b804d4a9a852faa7fe2ce0457cc2e23789547d22fd3cbe840efe5fd429.

What I take from this

Numerical parity isn’t a claim about every intermediate value. Compare the exact outputs of the exact compiled program you plan to run. Use debug taps to find where divergence starts, not to reclassify another artifact.
